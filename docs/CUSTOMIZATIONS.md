# custom 分支定制边界

最后核对：2026-09-07。本文根据定制分支的开发记录、提交历史和当前代码整理，目的是
上游同步时防止把定制功能当成普通文件差异而覆盖掉。

## 分支和版本约定

- `main` 只跟随 `upstream/main`，不放定制提交。
- `custom` 是实际开发、部署和发布分支。
- 同步上游时从 `custom` 创建临时集成分支，逐个判断上游提交实现的功能；独立功能可以
  cherry-pick，耦合功能必须手动移植，最后 fast-forward 合回 `custom`。
- 不能整条 rebase、整文件选择 `ours/theirs`，也不能因为文件同名就覆盖。
- 版本号按 [`UPSTREAM-SYNC.md`](UPSTREAM-SYNC.md) 处理：`package.json`、根部
  `package-lock.json` 两个版本字段、`public/sw.js` 和当前发布元数据保持一致。
- 数据库 migration 只追加，不改写已发布的 migration 编号或历史行为。

## 必须保留的定制功能

### 任务列表

- 任务列表是持久化的一等对象，层级是“全部 → 来源 → 具体列表”；只有一个全局“全部”，
  不要为每个来源再造一个“全部”。选择来源后可以重置为该来源的所有任务。
- 本地、CalDAV、Microsoft To Do 等来源保留各自的列表身份；列表的启用选择、来源/列表
  顺序和字母排序状态必须持久化。桌面端支持拖动分隔线，移动端使用来源和列表两层选择。
- 未选择的远端列表不能在刷新或全量同步时被默认重新勾选，也不能因为登录就自动拉取任务；
  Microsoft 连接阶段只加载列表和日历，用户保存选择后才同步。
- 只允许删除具体任务列表；“全部”、来源和虚拟“本地”不能删除。删除列表前逐项检查
  列表内任务是否都允许当前用户删除，混合列表只要有一项不允许就拒绝。实际删除要清理
  任务、子任务、提醒及关联数据，不能依赖 `ON DELETE SET NULL` 把任务变成“本地任务”。

### Microsoft To Do

- 使用任务列表映射、持久化启用选择、增量同步和明确的全量同步；连接账户不触发耗时的
  自动全量同步。完成状态、标题、描述、日期、提醒等普通字段可以双向同步。
- Microsoft 的优先级语义以星标/重要为准：Yuvomi 的 `urgent`/`high` 映射为 Microsoft
  的重要，其他级别映射为普通；从 Microsoft 导入时重要才是 `high`，未标记不伪造
  `medium`/`low`。
- 提醒时间按 Yuvomi 的家庭/显示时区转换，不能把本地墙上时间直接当 UTC，也不能把
  UTC 值重复转换。重复任务由 Microsoft 生成下一实例；Yuvomi 不本地复制一份。
- 已存在的 Microsoft 重复任务更新时不发送 `recurrence`，避免 Graph 的 PATCH 限制；
  这不禁止标题、描述、日期、提醒和完成状态更新。重复规则的修改/取消仍由 Microsoft
  端负责，直到同步协议另行解决。
- Microsoft `steps`/`checklistItems` 不映射为 Yuvomi 子任务。Yuvomi 子任务是真实任务，
  有独立 ID、可见性、权限和父子关系；To Do step 没有这些语义。
- Yuvomi 任务描述中的 Markdown `- [ ]` 清单是另一项原生能力：清单项可以直接点击，
  并回写描述（包括现有可同步的描述字段）；它不能被当作 Microsoft step 的兼容层，
  也不能在同步时删除。

### 日历和订阅

- Outlook 日历是双向同步；连接后先加载日历，用户选择后才导入。默认只回溯六个月，
  也支持绝对起始日期；双方同时修改必须进入冲突选择，不能静默覆盖。
- 日历时间遵循 Yuvomi 家庭时区。日期/时间字段区分墙上时间和带时区的瞬时值，不能
  通过浏览器或服务器的 UTC 默认值随意换算。
- ICS 订阅事件的“来源日历”和“同步目标”是两个概念：事件来源显示订阅名称，目标
  可以是“仅本地保存”。订阅颜色默认用于事件显示，用户明确修改事件颜色后才覆盖；
  订阅颜色为空时继续使用已有事件/继承回退逻辑。
- 日历视图同时显示任务的截止时间和提醒时间；议程视图将同一天的事件和任务放在同一
  列表中按时间排序，没有时间的项目按全天项目处理。只有提醒没有截止日期的任务也要
  按提醒日期出现。提醒存储格式是兼容历史的 UTC 无 `Z` 字符串，读取时必须先按 UTC
  解析，再转换到显示时区。

### 通知渠道

- Pusher 的提醒和即时通知（包括个人与家庭渠道）将 `remindAt`、`sentAt` 按家庭设置的时区
  转成可读时间；为空的可选字段不输出空行。只有配置了可信的 `BASE_URL` 才输出绝对的
  Yuvomi 链接，否则省略链接。通用 Webhook 继续保留原始 JSON、UTC 时间和相对路径契约。

- 通知分个人和家庭两层：普通用户使用个人 Webhook/Pusher，管理员可以管理家庭 Webhook/
  Pusher；不要把家庭通知管理误放到普通用户界面，也不要把两层合并成一个配置。
- 两层都支持可配置模板和测试发送。模板可包含任务/事件标题、描述、开始/截止日期与
  时间、提醒时间、状态、分类、内容和 Yuvomi 链接；空字段不要输出时区或伪造值。
- 个人模板和家庭模板保持同一套字段语义，但配置对象、权限和接收范围独立；管理员自行
  同时启用两层时可能收到两条，这是配置选择，不应偷偷覆盖个人设置。

### 资产

- 资产页面是内置功能，不是需要单独挂载的第三方容器或手动复制的模块。它复用 Inventory
  和现有 API，不创建第二套资产数据库，也不直接读写 `yuvomi.db`。
- 资产分个人资产和家庭资产：个人可管理自己的资产并按可见性共享，家庭资产由管理员
  管理并可指定可见范围；资产分组、状态、购买/出售日期和价格、目标使用天数都属于
  定制数据模型。
- 资产成本实时计算，不把 `days_used` 或日均成本写入数据库。图片搜索在资产名称旁的
  弹窗中完成，可选择 Google、DuckDuckGo、Brave、Openverse 等来源；不能把联网搜图做成
  依赖独立服务或要求每台新机器手动拷贝模块。
- 首页概览可以显示资产摘要；资产模块沿用 Yuvomi 的主题、深色模式、响应式布局和现有
  Inventory 图片/分类能力。

### 界面、时区和数据契约

- 任务桌面端固定头部槽位，来源和列表区域可调整宽度；移动端来源与列表分行，来源可
  横向选择，列表再选择。搜索弹层重新打开时，已有文字的光标必须放在末尾且不能拉起
  键盘后立即失焦。
- 日历和资产页的桌面、移动端头部都遵循固定槽位：模块图标只由 Shell 显示一次。资产页
  移动端的模块图标与“资产”标题必须同一行，资产搜索字段位于下一行；日历的搜索入口
  在标题行右侧，日期导航和视图切换保持独立位置，不让搜索单独占一行。资产总览卡的
  指标切换和主题入口固定在卡片标题行，不能因移动端竖排而掉到指标下方。
- 任务默认显示“待处理”，筛选器、来源、列表、历史/看板/列表视图的槽位不能在不同
  视图间跳动；任务标题和描述要允许换行。
- 所有定制新增字段都必须通过现有 `/api/v1` 合约、权限和可见性规则处理；不能为了
  前端方便绕过权限或直接访问数据库。

## 高风险文件和区域

上游同步时至少逐项检查下列路径的语义，不得整文件替换：

- `server/routes/tasks.js`、任务列表相关服务、`server/services/microsoft-todo.js`、
  `public/pages/tasks.js`、`public/styles/tasks.css`；
- `server/routes/calendar/`、`server/services/outlook-calendar.js`、ICS 订阅服务、
  `public/pages/calendar.js`、`public/utils/event-color.js`、日历样式；
- `server/routes/notifications.js`、通知服务/provider、通知设置页、模板文档和所有
  本地化文案；
- Inventory/asset 相关页面、路由、服务、dashboard widget 和迁移；
- `public/router.js`、`public/nav-icons.js`、`public/pages/dashboard.js`、dashboard widget；
- `server/db.js`、schema/migrations、`package.json`、`package-lock.json`、`public/sw.js`。

## 上游同步前后的检查

1. 先确认工作区没有未提交修改会被覆盖，确认 `main`、`custom` 和 `upstream/main` 的
   拓扑；更新 `main` 只能 fast-forward 到 `upstream/main`。
2. 对每个上游提交写清楚它实现的功能、与 custom 的重叠点、是否能组合，以及采用、手动
   移植或跳过的原因。只有同一语义功能才适用“以上游为准”。
3. 检查 migration、API 字段、权限/可见性、同步身份、冲突策略、时区和移动/桌面布局；
   文件冲突不是解决方案。
4. 运行受影响模块测试和基础测试，至少检查 `git diff --check`、完整集成分支 diff、
   提交历史、工作区状态和版本号。
5. 明确确认 Microsoft To Do、Outlook/ICS 日历、任务列表、通知渠道、资产和首页 widget
   都仍然存在，再 fast-forward 合并临时集成分支到 `custom`。
